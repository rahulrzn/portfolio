# Content repository review

Reviewed on 2026-11-14. Scope: `src/content/**`, `src/components/ContentImage.tsx` and `src/components/ExternalLink.tsx`. Requirements: `PRODUCT.md`, `docs/content-source.md`, implementation plan task 1, and brief sections 7–8. This is a review of the current files; no Git repository is present.

**Spec compliance: changes required.** The typed models, explicit browser-local publication, safe text/link boundaries and normal draft isolation are implemented. Recovery and backup failure paths below still violate the required preservation and safe export/restore behavior. Centralized future API configuration (`VITE_API_BASE_URL`) is also absent from the inspected project; the repository interface itself is a useful replacement boundary.

**Code quality: changes required.** No executable URL or arbitrary HTML rendering issue was found in this scope. The content commit validates before writing, keeps the prior valid snapshot before the authoritative single-key write, and preserves the in-memory snapshot on failed writes. Portable import validates every decoded image before staging, generates fresh image IDs, and attempts rollback if a later stage or content commit fails. The outstanding problems are concrete recovery and round-trip cases rather than architectural objections to frontend-only storage.

## Findings

1. **P1 — A read failure discards an already valid in-memory state.** `src/content/repository.ts:18–24`, `:50`. After the repository has loaded or published valid edited content, a subsequent `refresh()` whose storage read throws replaces both published and draft content with defaults. If storage resumes and the user saves an edit, that default-based snapshot can overwrite the previously valid persisted content and recovery copy. Keep the current valid snapshot on refresh failure, attach a warning, and use defaults only when no valid snapshot has ever been available. Fresh diagnostic: publishing the name `Retained custom name`, then making `getItem` throw and calling `refresh()`, produced published name `Rahul Reji R.`. Additionally, initial `createRepository(undefined)` has an empty warning because the optional storage read never throws; surface the unavailable-storage warning at initialization too.

2. **P2 — A valid plain export can be rejected by its own importer.** `src/content/repository.ts:14`, `:30–31`, `:55–56`. The save limit counts compact JSON, while `exportSnapshot()` adds indentation and the importer applies the same raw-character limit to that larger representation. Fresh diagnostic with 37 valid projects: compact saved content was 964,322 characters, its export was 1,020,720 characters, and re-import failed as an invalid backup. Validate a bounded parsed/canonical representation or give raw input sufficient headroom, while retaining an independent abuse bound.

3. **P2 — Successful portable imports retain unreachable image blobs.** `src/content/backup.ts:6`, `:20–23`. Exports include image references from both draft and published content. Import stores every supplied image under a new ID, but remaps and commits only draft references. Any image used only by the backup's published snapshot, or included without a draft reference, is never referenced in the resulting repository. Repeated imports therefore consume IndexedDB quota with assets that no editor can remove. Validate all payload images, but only stage images referenced by the draft being imported; alternatively remove all staged images that the committed draft does not reference. Preserve the destination's published images until explicit publication.

4. **P2 — Backup image capacity disagrees with the content model.** `src/content/backup.ts:5–11`, `src/content/schema.ts:30`, `:42`. Each snapshot supports 60 project images and a profile image; distinct draft and published references can therefore total 122 images. The portable schema allows only 80. A valid content state containing 81 small images cannot be exported even when it is well below the 20 MB total limit. Make the portable limit compatible with every supported content state, or constrain content consistently with a useful validation message before saving.

5. **P2 — Image storage failures can silently produce incomplete backups.** `src/content/images.ts:21`, `src/content/backup.ts:10`. `imageStore.get` converts any IndexedDB error to `null`, and export silently skips that reference. A user with valid uploaded images but temporarily denied image storage receives a successful-looking backup containing the original `image:` references without their bytes. Import on another device loses those images. Keep public image fallback tolerant, but expose the difference between a missing asset and a storage failure to backup export. Report omitted assets or stop the export with an understandable recovery instruction.

## Reviewed safeguards

- Strict Zod schemas and bounded collections reject unknown content fields, unsupported versions, duplicate project slugs and duplicate IDs in their respective collections. URLs allow only HTTP/HTTPS and reject embedded credentials; image references allow constrained local IDs, the supplied portrait asset and validated HTTPS references.
- Draft and published data are independently cloned at initialization and publication. Saves/imports update draft only; revert and reset stage changes rather than directly changing public content. Public filtering of per-project/per-research draft status belongs to the public rendering review.
- `ContentImage` releases blob URLs and handles missing/failed images with the supplied fallback. `ExternalLink` revalidates URLs and uses `noopener noreferrer` with a new tab.
- Uploads check advertised MIME, a 3 MB per-image limit, decoding and pixel bounds. Portable imports check envelope/schema version, duplicate image payload IDs, per-image Base64 bounds, total image size and decoding before any image writes; later failures trigger best-effort cleanup.
- Public/admin content consumers use repository/context and image service methods. No direct content-storage dependency or arbitrary HTML rendering exists in the reviewed components. Rendering of long content, dialogs, text fields and final backend documentation require the parent public/admin reviews.

## Evidence and limits

The parent reported eight existing Vitest tests and TypeScript checks passing. Those unchanged checks were not rerun. Fresh in-memory storage diagnostics executed the real repository via Vite's module loader and confirmed findings 1 and 2; all diagnostic commands completed without editing source files. Findings 3–5 follow the inspected image-reference/write/error control flow. Real-browser decoding, IndexedDB transaction abort/rollback behavior and quota-bound portable-import integration are not covered by the existing image test, which only exercises file metadata validation. Add targeted failure-class tests while fixing these findings, including read denial after a valid load, portable/plain round trips near limits, published-only images, missing/unreadable image storage and cleanup on failed content commit.
